# 架构与数据流

1. 本机文件选择器读取音频 Blob，Web Audio 解码得到时长和波形；文件存入 IndexedDB。
2. TXT/LRC 解析保留完整歌词与可选秒数。录谱捕获共享音乐时钟下的真实接触时间；双指同拍保存一个 double 事件及两个 rawTimes。
3. 编辑器向 generation.worker 发送 GenerationRequest，Worker 生成速度为每秒 2 世界单位的主路线，按段落反射成第二条等长路线；双球在两端相遇。
4. 路线和歌词字群使用同一份世界数据。文字按完整句块排入路线周围，整块移动，字形不被道路切割。无法清楚生成的双球或岔路会提供警告并保留输入时间。
5. Engine 按显式事件列表判定，全屏输入由最近事件决定归属；两条路线共用三次预读。分裂汇合没有额外判定。岔路两侧时间与长度一致。
6. AudioContext 输出时钟驱动球、判定与录谱；Renderer 独立处理相机和短促光效。暂停清理触点并保存音乐位置，校准不改变录音尾部。
7. Entry 保存作品与多份 Chart；Draft 保存未完成的输入。ZIP 以清单引用 JSON 与音乐，音频 SHA-256 校验，内容指纹重算用于隔离修改后的纪录。

UI 与游戏共用一个应用视口；自然横屏采用对页与侧边 HUD，强制横屏旋转整个坐标系并转换触点与方向键。世界尺度按短边计算，安全区随布局映射。

耗时的地图编排在 Worker 中进行。字体与图形以缓存图块绘制；音频以 Web Audio 直接播放，输入不等待下一次动画帧才提交判定或声音。

目前球沿预编排路线移动，歌词是视觉地图实体；路线清空通过生成/导入校验完成，不在每帧让球重新寻找碰撞出口。规则与空间数据独立，便于以后扩展平滑路线及更精细的字形掩码。

小球的位置直接使用输出音乐时钟。新生成的两条岔路在拍点后共享 80ms 的直行段，手势在这段内到达仍可选择任一路；两路的提前窗口和截止时间相同。选择发生时当前坐标完全相同，随后沿已选路线继续匀速运动，不需要全局画面延迟、停球或瞬移。旧谱面没有共同行进段时，在实际分叉前完成选择。
